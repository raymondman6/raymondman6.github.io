## 先接通，再接管

1. 阅读本目录 README、API 与顾问规则。保持 GitHub 的网页入口；选择当前环境实际可用的、支持私人共享记录的后台。
2. 若使用 Sites，重新确认官方 skill 和 helper 可执行；按当时的官方工作流准备有 D1、R2 的完整服务，保留托管平台认证。现有 Worker 业务逻辑可移入支持的完整 starter，不把未包含 SQL migrations 的简易静态打包当成完整部署。
3. 配置私有 DB、私有图片存储、精确的前端来源和两种后台凭据。秘密仅保存于托管平台；`config.js` 只填写公开 API 地址和管理入口。
4. 妹妹需要能在她的设备上打开信箱并留言。Sites 私有外部访客邀请仍要求受邀的 ChatGPT 账号；不要把邮箱邀请当成免账号入口。公开网页入口、私人记录的邀请访问权限是不同设置；涉及改变 Site 外层访问范围时按原授权和平台要求处理。
5. 以测试问题验证：妹妹端提交 → 独立客户端读取 → dot 写回答案 → 前端回读成功 → 给哥哥同步全文 → 确认收到 → 记录已同步。再测试一次追问和一次重试，确保没有重复回答。真实邀请链接在管理入口生成并交给哥哥转发，不放公开源码。
6. 验证成功才将 `config.js` 改成 `ready:true`。获得可用于未来任务的受支持连接，例如发布 Site MCP 并完成 Install/Connect，不能依赖当前一次性的浏览器或临时凭据。
7. 默认按香港时间（Asia/Hong_Kong，UTC+8）每小时检查一次。先查已有任务，复用同一信箱已有任务，避免重复；保存任务并确认实际频率、任务 ID、启用状态。哥哥也可随时要求立即检查。任务需要向哥哥本人现有 dot 对话投递结果，不要另外创建属于本普通聊天的同类任务来替代。

## 每次检查的顺序

1. 一轮任务串行执行。先读取未同步的回复，补发此前未送达哥哥的内容。
2. 读取待回答问题、必要前文和最新已确认学生档案。只处理真人新增的提问或追问，忽略 AI 自己的回复。
3. 按 `advisor-rules.md` 解答。使用读取到的 `last_human_id` 作为 `through_message_id` 回写。409 表示妹妹补充了内容，重新读帖后再回答；请求结果不确定时先回读，不能盲目重发。
4. 回写成功后再回读核实。需要补充资料时使用 `needs_info`，其余用 `replied`。新的真人留言会重新成为待回答。
5. 从同步记录读取本次原问题、附件、完整答案和原帖链接，在哥哥本人 dot 对话发送。太长可编号分段，全部送达后再 acknowledge。每份通知带同步记录 ID，恢复任务时先检查该 ID 是否已发送，减少重复通知。
6. 回复去重与通知去重分别处理：回复成功而通知失败时，只补发通知。送达结果不确定时核查 dot 对话记录，再决定补发或确认；不能保证第三方消息投递的绝对恰好一次。
7. 一轮结束记录 heartbeat。它只记录实际检查时间，不代表已创建或启用定时任务。没有新问题、也没有待补发内容时不通知哥哥。

## 权限与故障

网站记录和哥哥通知的成功状态分别核实。任何缺失的访问、连接、任务、投递能力明确报出，不把完成一次运行等同于用户已收到。单条失败保留待办，继续处理其他独立问题。不要向新的收件人或公开位置发送学生记录。
